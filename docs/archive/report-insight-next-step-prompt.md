# 리포트 인사이트 다음 단계와 LLM 작업 프롬프트

> 과거 설계·검토 자료다. 본문의 상태, 구현 지시, 다음 단계는 작성 당시 기준이며 현재 개발 요구사항이 아니다.
> 고도화 작업에서는 현재 코드·테스트와 새 요구사항을 확인한 뒤 필요한 내용만 참고한다.

## 다음 단계

현재 구현은 인사이트의 데이터 형식과 상세 화면을 만들었지만, 기존 리포트에는 아직
`insight`가 없다. 다음 단계는 **기존 요약·태그를 건드리지 않고 인사이트만 안전하게
백필하는 별도 파이프라인**을 만드는 것이다.

진행 순서는 다음과 같다.

1. 인사이트 생성을 기존 `summarize_pending`에서 분리한다.
2. 기존 `summary`와 원문을 입력으로 `insight`만 생성하는 프롬프트와 검증 함수를 만든다.
3. `--backfill-insights --limit N`으로 소량부터 재실행할 수 있게 한다.
4. 기존 `summary`, `desk`, `industries`, `themes`, `tagged_at`이 바뀌지 않는지 테스트한다.
5. 5~10건을 먼저 생성해 사람이 품질을 검토한 뒤 전체 리포트로 확대한다.
6. 전체 백필 후 Next.js 빌드와 모바일·다크 모드 화면을 확인한다.

이렇게 분리하는 이유는 인사이트가 없다는 이유만으로 기존 요약과 분류를 다시 생성하면
불필요한 LLM 비용이 들고, 이미 확정된 태그가 달라져 주간 집계까지 흔들릴 수 있기 때문이다.

## LLM에게 전달할 프롬프트

아래 블록을 그대로 복사해 코딩 에이전트에게 전달한다.

```text
당신은 `/workspace/f_report` 저장소를 수정하는 시니어 엔지니어다.

목표:
기존 개별 리포트에 `insight`를 안전하게 백필할 수 있는 전용 파이프라인을 구현하라.
인사이트가 없더라도 기존 `summary`와 분류 결과를 다시 생성하거나 변경하면 안 된다.

먼저 반드시 확인할 것:
1. 저장소와 상위 경로에 있는 `AGENTS.md`를 모두 확인하고 적용 범위를 지켜라.
2. `README.md`, `skills/summarize-report/SKILL.md`, `scripts/process_reports.py`,
   `web/lib/data.ts`, `web/app/reports/[id]/page.tsx`, 관련 테스트를 읽어라.
3. 현재 git diff와 최근 커밋을 확인하고 기존 작업을 되돌리지 마라.

구현 요구사항:
1. `skills/generate-report-insight/SKILL.md`를 새로 만들고 인사이트 관점을 아래처럼 고정하라.
   - change: 기존 전제와 비교해 무엇이 달라졌는가
   - implication: 기업·산업·시장 흐름을 이해하는 데 왜 중요한가
   - watch_points: 해석을 확인할 관찰 지표나 사건 1~3개
   - 투자 추천, 목표 수익률, 원문에 없는 사실, 외부 최신 정보는 생성하지 않는다.
   - 원문에 비교 기준이 없으면 과거 사실을 만들지 말고 현재 리포트가 강조한 변화를 쓴다.
2. `scripts/process_reports.py`에서 인사이트 생성을 요약 생성과 분리하라.
   - 기존 `summarize_pending`은 `summary`가 없는 리포트만 처리해야 한다.
   - 새 함수는 `report_type == "individual"`, `summary` 존재, `insight` 부재,
     `pdf_error` 부재인 리포트만 처리해야 한다.
   - 입력에는 리포트 메타데이터, 기존 `summary`, `pdf_text` 또는 `preview_text`를 넣어라.
   - 출력은 다른 말 없이 `{"insight": {...}}` JSON 하나만 요구하라.
   - 기존의 인증 오류·사용량 한도·연속 실패 처리 규칙을 재사용하라.
3. CLI에 `--backfill-insights` 플래그를 추가하라.
   - 플래그가 있을 때만 기존 리포트의 누락 인사이트를 처리한다.
   - `--limit`을 공유하거나 명확한 별도 limit 옵션을 제공하되 도움말에 의미를 써라.
   - 신규 리포트는 기존 요약 단계에서 summary와 insight를 함께 생성해도 된다.
4. 인사이트 전용 실행은 아래 필드를 절대 변경하지 않아야 한다.
   - `summary`, `desk`, `industries`, `themes`, `tagged_at`
   - 산업·테마 인덱스, 산업 브리핑, 주간 인사이트, 일간 다이제스트
   단, 대상 레코드의 `insight`와 인사이트 생성 시각 필드는 추가할 수 있다.
5. `insight_generated_at`을 추가하고 웹의 `Report` 타입에도 선택 필드로 반영하라.
6. 검증은 순수 함수로 유지하고 다음을 거부하라.
   - 빈 change 또는 implication
   - 배열이 아니거나 비어 있는 watch_points
   - 3개를 초과한 watch_points는 앞의 3개만 유지
   - 공백뿐인 항목은 제거
7. 테스트를 추가하라.
   - 대상 선택 조건
   - 정상 응답 정규화
   - 잘못된 응답 거부
   - 백필 후 기존 summary/태그 불변
   - daily_series 제외
   테스트에서 실제 LLM이나 네트워크를 호출하지 말고 mock을 사용하라.
8. README에 사용 예시를 추가하라.
   - 먼저 5건: `python scripts/process_reports.py --limit 5 --backfill-insights`
   - 검토 후 전체 실행 방법
   - 실행 전후 git diff로 insight 외 필드가 바뀌지 않았는지 확인하는 절차

품질 기준:
- 인사이트는 단순 요약 반복이 아니라 변화 → 의미 → 확인의 연결을 보여야 한다.
- 그러나 원문 근거를 넘어선 추론이나 매수·매도 권고는 금지한다.
- 기존 데이터가 없는 상태에서도 빌드가 깨지지 않아야 한다.
- 함수와 옵션 이름은 역할이 분명해야 하며, import 주위에 try/except를 두지 마라.

검증 명령:
- `python -m unittest discover -s tests -v`
- `python -m py_compile scripts/process_reports.py`
- `cd web && npm run build`
- `git diff --check`

완료 보고에 포함할 것:
- 바뀐 파일과 핵심 설계
- 기존 필드 불변을 보장한 방법
- 실행한 테스트와 결과
- 실제 LLM 백필을 실행하지 않았다면 그 사실과 실행 명령
- 남은 리스크

주의:
유효한 LLM 인증 정보가 없다면 실제 백필을 실행하지 마라. 샘플 인사이트를 운영 데이터에
임의로 써 넣지 말고, 구현과 mock 테스트까지만 완료하라.
```

## 백필 결과를 사람이 검토할 기준

첫 5~10건은 다음 기준으로 확인한다.

- `change`가 원문에 없는 과거 상태를 지어내지 않았는가?
- `implication`이 핵심 포인트의 단순한 재진술이 아니라 “그래서 무엇을 이해해야 하는가”에
  답하는가?
- `watch_points`가 “시장 상황을 지켜본다”처럼 모호하지 않고 실적, 수요, 가격, 정책 일정 등
  실제로 확인 가능한 항목인가?
- 목표주가나 투자의견을 근거 없이 확대 해석하지 않았는가?
- 세 필드를 읽었을 때 하나의 논리적 흐름으로 이어지는가?

위 기준을 통과한 뒤에만 limit을 늘린다. 품질이 낮으면 데이터 전체를 생성하기 전에
`generate-report-insight` 스킬의 예시와 금지 규칙부터 조정한다.
