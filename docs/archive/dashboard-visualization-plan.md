# 리서치 흐름 대시보드 시각화 계획

> 과거 설계·검토 자료다. 본문의 상태, 구현 지시, 다음 단계는 작성 당시 기준이며 현재 개발 요구사항이 아니다.
> 고도화 작업에서는 현재 코드·테스트와 새 요구사항을 확인한 뒤 필요한 내용만 참고한다.

## 1. 결정 요약

이 대시보드의 목적은 **많이 나온 리포트를 세는 것**이 아니라, 사용자가 짧은 시간 안에
`이번에 무엇이 달라졌는지 → 어떤 근거가 반복되는지 → 어디까지 믿을 수 있는지 → 무엇을 더 읽을지`를
판단하게 돕는 것이다. 따라서 첫 화면은 종목 시세판이나 차트 모음이 아니라 다음 세 층으로 구성한다.

1. **상황 파악**: 최신 데이터 시점, 이번 주 핵심 서사, 전주 대비 새로 등장·확대·약화한 테마
2. **관계 이해**: 테마가 어떤 산업과 연결되고 어떤 리포트가 그 판단을 뒷받침하는지
3. **근거 확인**: 산업·테마의 시계열과 원문 요약을 거쳐 개별 리포트까지 드릴다운

핵심 시각화는 `주간 테마 변화표`, `테마×산업 히트맵`, `산업 관심도 스몰 멀티플` 세 가지로 제한한다.
현재 데이터만으로 계산할 수 없는 주가 수익률, 컨센서스 변화, 감성 점수는 1차 범위에서 제외한다.

### 왜 지금 한눈에 안 들어오는가

원인은 단순히 **텍스트 양이 많아서**가 아니다. 현재 화면은 잘 요약된 글을 페이지별로 나열하지만,
서로 다른 중요도의 정보가 거의 같은 카드·문단·칩으로 표현된다. 사용자는 매번 글을 읽어야만
`새로운 것`, `반복되는 것`, `근거가 많은 것`을 구분할 수 있다. 즉 문제는 정보량보다 다음 세 가지다.

1. **비교 기준 부재**: 이번 주 숫자만 있고 직전 주와 무엇이 달라졌는지 바로 보이지 않는다.
2. **시각적 위계 부재**: 결론, 근거, 메타데이터가 비슷한 무게로 보여 스캔 경로가 없다.
3. **텍스트와 근거의 거리**: 주간 서사에서 관련 산업과 원문 목록으로 이동하며 맥락이 끊긴다.

따라서 글을 무조건 줄이는 것이 답은 아니다. 홈에서는 결론을 **상태·순위·변화·관계**로 먼저
압축하고, 설명문은 선택했을 때 펼치며, 마지막에 근거 리포트를 보여 주는
`overview → zoom/filter → details on demand` 구조로 바꾼다. 목표는 텍스트 삭제가 아니라
**읽기 전에 비교할 수 있게 만드는 것**이다.

## 2. 현재 상태와 제약

### 이미 활용 가능한 데이터

- 개별 리포트: 발행일·시각, 제목, 애널리스트, 데스크, 산업(0~2), 테마(1~3), 한 줄 요약,
  핵심 포인트, 리스크, 투자의견·목표주가(있는 경우), 원문 링크
- 주간 집계: 주차별 전체 리포트 수, Top 테마와 근거 리포트, 브리핑이 생성된 산업과 근거 리포트
- 일간 집계: 핵심 문장, 데일리 코멘트, 산업 브리핑 업데이트, 개별 리포트 목록
- 탐색 축: 데스크, 산업, 테마, 애널리스트, 날짜, 리포트 유형

### 데이터가 의미하는 것

- 리포트 수는 **하나증권 리서치의 관심도**이지 시장 중요도, 투자 매력도, 상승 확률이 아니다.
- 같은 애널리스트의 연속 리포트는 독립된 근거 여러 개로 볼 수 없다.
- 테마 이름은 병합 규칙이 바뀌면 과거 집계도 달라질 수 있다.
- 산업 브리핑은 주 2건 이상일 때만 생성되므로, 브리핑 부재가 산업 이슈 부재를 뜻하지 않는다.
- `daily_series`는 중복 카운트를 막기 위해 산업·테마 빈도 및 추세 집계에서 제외한다.
- 현 데이터 보유 기간이 짧아 장기 추세나 계절성을 말할 수 없다. 최소 8주가 쌓이기 전에는
  `전주 대비`만 제공하고, 8주 이동 기준선은 충분한 데이터가 쌓인 뒤 활성화한다.

모든 정량 카드와 차트에는 `리포트 언급량 기준`, 집계 기간, 표본 수, 마지막 갱신 시각을 표시한다.

## 3. 사용자와 핵심 질문

주 사용자는 매일 모든 리포트를 읽기 어려운 **개인 학습자** 한 명이다. 매수·매도 결정을 자동화하는
도구가 아니라 시장과 산업의 논리 변화를 추적하는 도구로 정의한다.

| 이용 순간 | 사용자가 묻는 질문 | 대시보드가 주는 답 | 목표 시간 |
|---|---|---|---:|
| 매일 첫 방문 | 어제/오늘 새로 달라진 것이 무엇인가? | 최신 핵심 3줄, 새 테마, 갱신 산업, 신규 리포트 | 2분 |
| 주말 복기 | 이번 주를 관통한 논리와 다음 확인점은? | 주간 서사, 전주 대비 테마 변화, 일정·체크포인트 | 5분 |
| 관심 이슈 탐색 | 이 테마가 어떤 산업에 영향을 주며 근거는 무엇인가? | 테마×산업 관계, 주차별 변화, 근거 리포트 | 3분 |
| 산업 학습 | 이 산업에 대한 관점이 최근 어떻게 변했나? | 주간 언급량, 핵심 논지·리스크, 관련 테마, 브리핑 | 5분 |
| 사실 확인 | 요약의 원문 근거를 어디서 확인하나? | 리포트 상세와 증권사/PDF 원문 링크 | 1분 |

북마크·알림·포트폴리오 관리보다 **변화 탐지와 근거 추적**을 우선한다.

### 3.1 기대효과

이 설계의 효과는 “차트가 생겨서 보기 좋아진다”가 아니라, 같은 리서치 데이터로 더 빠르고 덜 왜곡된
판단을 내릴 수 있다는 데 있다. 아래 수치는 보장된 성과가 아니라 구현 후 사용성 테스트로 검증할 목표다.

| 현재 사용 경험 | 개발 후 기대 경험 | 사용자 이점 | 검증 기준 |
|---|---|---|---|
| 최신 주간·일간 문단을 처음부터 읽음 | 상태 바와 변화표에서 신규·확대·약화를 먼저 확인 | 오늘 읽을 주제를 빠르게 선별 | 변화 테마 30초 이내 발견 |
| 누적 건수만 보고 최근 이슈인지 판단하기 어려움 | 이번 주/전주/최근 4주를 같은 기준으로 비교 | 오래 누적된 테마와 새로 부상한 테마를 구분 | 양 주 건수와 증감을 한 화면에서 확인 |
| 테마 칩과 산업 목록을 각각 열어 봄 | 테마×산업 히트맵 셀에서 교차 근거로 이동 | 하나의 이슈가 어디에 파급되는지 빠르게 파악 | 관련 산업·리포트에 3클릭 이내 도달 |
| 긴 설명 속에서 중요한 문장을 다시 찾음 | 결론 1문장·2줄 요약 후 필요할 때 상세 펼침 | 반복 방문 시 읽는 양과 인지 부하 감소 | 홈의 기본 노출 문장 수와 체류 시간 비교 |
| 리포트 여러 건을 독립적인 근거로 오해할 수 있음 | 고유 애널리스트·데스크 수와 근거 집중 경고 표시 | 반복 발행과 교차 검증을 구분 | 집중 경고가 표본과 일치하는지 검사 |
| 차트나 목록의 숫자를 원문과 별도로 추적 | 모든 셀과 행이 구성 리포트 목록으로 연결 | 요약을 신뢰하되 필요하면 즉시 검증 | 요약에서 원문까지 2클릭 이내 도달 |
| 가공 작업의 지연·실패를 화면에서 알기 어려움 | 최신 수집·가공 시각과 오류 건수를 상단 표시 | 오래된 데이터를 최신으로 오인하는 위험 감소 | 첫 화면에서 10초 이내 상태 확인 |

#### 사용자 관점의 핵심 이점

1. **읽기 전에 우선순위를 정한다.** 전체 다이제스트를 순서대로 읽지 않고, 새로 등장하거나 커진
   테마부터 선택할 수 있다.
2. **점이 아니라 흐름으로 기억한다.** 개별 리포트를 날짜별 사건으로 소비하는 대신, 같은 테마가
   몇 주 동안 어떤 산업으로 번지는지 이어서 볼 수 있다.
3. **요약과 근거를 함께 본다.** 차트 숫자에서 해당 숫자를 만든 리포트까지 바로 내려가므로
   요약만 보고 단정하는 위험을 줄인다.
4. **근거의 양보다 다양성을 본다.** 리포트 5건이 사실상 한 애널리스트의 반복 의견인지,
   여러 데스크가 독립적으로 다룬 이슈인지 구분할 수 있다.
5. **반복 방문 비용이 낮아진다.** 이미 읽은 긴 설명을 다시 훑지 않고 전주 대비 달라진 부분부터 본다.

#### 운영·개발 관점의 핵심 이점

1. **파이프라인 이상을 조기에 발견한다.** 미요약·PDF 오류·최신 발행일을 노출하면 수집 성공과
   대시보드 최신성을 별도로 확인할 수 있다.
2. **숫자 불일치를 줄인다.** `DashboardSnapshot`의 공통 집계를 카드·차트·표가 함께 사용하므로
   화면마다 다른 방식으로 리포트 수를 세는 문제를 예방한다.
3. **기능 확장이 쉬워진다.** 기간·산업·테마 필터를 URL과 공통 모델로 관리하면 이후 북마크나 알림도
   같은 상태 표현을 재사용할 수 있다.
4. **정적 배포의 장점을 유지한다.** 집계는 빌드 단계에서 만들고 상호작용 영역만 hydration하므로,
   별도 분석 서버 없이 현재 Git/Vercel 운영 방식을 유지할 수 있다.
5. **도입 실패 비용을 제한한다.** ECharts가 성능·접근성 기준을 통과하지 못하면 동일 데이터 표를
   CSS Grid로 제공하는 fallback이 있어 라이브러리에 제품 구조가 종속되지 않는다.

#### 기대하지 말아야 할 효과

- 언급량이 많은 테마의 수익률이 더 높다는 의미는 아니다.
- 시각화만으로 리서치 내용의 정확성이나 태깅 품질이 개선되지는 않는다.
- 8주 미만 데이터에서는 장기 추세·계절성·이례치 판단이 유효하지 않다.
- 실제 시간 절감과 이해도 향상은 아래 성공 기준으로 측정하기 전까지 가설로 취급한다.

## 4. 정보 구조와 이동 원칙

### 권장 내비게이션

`홈(Overview) / 주간 / 일간 / 탐색 / 테마 / 산업`

- **홈**은 결론과 이상 징후를 보여 주고, 상세 내용은 각 허브로 보낸다.
- **주간·일간**은 현재처럼 생성된 편집 콘텐츠를 보존하되, 관련 차트와 리포트 링크를 결합한다.
- **탐색**은 기존 전체 리포트 검색·필터 화면의 이름을 사용자 과업 중심으로 바꾼다.
- **테마·산업**은 목록이 아니라 비교 가능한 현황판으로 먼저 보여 주고 세부 페이지로 진입시킨다.
- 모든 차트의 막대·셀·범례는 필터 또는 상세 페이지 링크로 동작해야 한다.
- URL에 기간과 필터를 반영해 새로고침·공유 후에도 같은 상태가 유지되게 한다.

### 공통 필터

- 기간: `이번 주 / 최근 4주 / 최근 8주 / 직접 선택`
- 데스크, 산업, 테마, 애널리스트
- 기본값은 `individual만`; 사용자가 명시적으로 선택할 때만 `daily_series 포함`
- 필터 적용 시 카드, 차트, 근거 목록의 모집단이 모두 함께 바뀌고 `n=건수`를 갱신한다.

## 5. 화면별 상세 설계

### 5.1 홈 — 2분 안에 변화를 찾는 화면

위에서 아래로 다음 순서를 권장한다.

1. **데이터 상태 바**
   - `마지막 수집`, `마지막 가공`, `최신 발행일`, `미요약/추출 실패 건수`
   - 최신 발행일이 평일 기준 1일 이상 뒤처지거나 실패 건수가 있으면 경고색 사용
2. **이번 주 한눈에**
   - 현재 주간 인사이트의 한눈에 문단을 3~5문장으로 표시
   - `근거 리포트 n건`, `주간 전체 보기` 링크 제공
3. **무엇이 달라졌나**
   - `신규`: 전주 0건, 이번 주 1건 이상
   - `확대`: 이번 주 건수 − 전주 건수가 양수
   - `지속`: 양 주 모두 등장하고 증감이 0
   - `약화`: 전주보다 감소
   - 상위 5개만 보여 주며 `+3건`처럼 절대 변화량과 양 주의 건수를 함께 표기
4. **테마×산업 미니 히트맵**
   - 행은 이번 주 Top 테마 5개, 열은 해당 기간 상위 산업 8개
   - 셀은 고유 리포트 수. 클릭하면 해당 테마+산업으로 필터된 근거 목록 노출
5. **오늘/최근 발행일 핵심 3줄**
   - 휴일에는 달력상의 오늘이 아니라 실제 최신 개별 리포트 발행일을 명시
6. **산업 변화**
   - 최근 4주 상위 산업 6개의 주간 언급량 스몰 멀티플
   - 2건 미만 주는 `브리핑 없음`으로 표시하되 0건과 구분
7. **최근 리포트**
   - 8~12건, 한 줄 요약과 태그, `새 항목` 표시. 전체 탐색으로 연결

홈에서 총 리포트 수, 테마 수처럼 행동을 유도하지 못하는 누적 KPI는 전면에 두지 않는다.

### 5.2 주간 — 서사와 전주 대비를 함께 읽는 화면

- 상단: 주차 선택, 집계 기간, 전체 개별 리포트 수, 직전 주 대비 증감
- `이번 주 한눈에` 다음에 **테마 변화표**를 둔다.

| 열 | 의미 |
|---|---|
| 테마 | 대표 테마명과 상세 링크 |
| 이번 주 / 전주 | 고유 개별 리포트 수 |
| 변화 | 신규·확대·지속·약화 배지와 증감 |
| 근거 다양성 | 고유 애널리스트 수 / 고유 데스크 수 |
| 연결 산업 | 상위 3개 산업 |

- 이후 기존의 테마별 `무슨 일이 있었나 / 어떻게 보나 / 왜 중요한가`를 아코디언으로 제공한다.
- 근거 리포트 ID 문자열은 제목 링크 목록으로 변환한다.
- `다음 주 체크포인트`는 날짜순 타임라인으로 표시하되, 원문에 명시된 일정만 사용한다.
- 이전/다음 주 비교 시 미래 날짜가 섞이지 않도록 주차 경계를 ISO 주차로 고정한다.

### 5.3 일간 — 새 정보와 기존 논리의 연결

- 핵심 3줄 각각에 관련 리포트 링크와 산업·테마 태그를 붙인다.
- `새 테마`, `기존 테마 재등장`, `산업 브리핑 갱신`을 별도 배지로 구분한다.
- 데일리 시리즈와 개별 리포트를 시각적으로 분리해 중복으로 오해하지 않게 한다.
- 날짜별 리포트 목록은 데스크별 접기/펼치기를 유지하고, 상단에 산업·테마 빠른 필터를 둔다.
- 달력 히트맵은 초기에 만들지 않는다. 발행량이 영업일·휴일에 좌우돼 정보 가치가 낮다.

### 5.4 테마 허브와 상세 — 이슈의 수명과 파급 경로

**허브**

- 기본 정렬은 누적 건수가 아니라 `최근 4주 언급량`, `이번 주 증감`, `최근 등장일` 중 선택하게 한다.
- 각 행에 스파크라인, 이번 주/4주 건수, 고유 애널리스트 수, 연결 산업 수를 표시한다.
- 1회 등장 테마는 `단발` 배지로 표시해 반복 이슈와 구분한다.

**상세**

- 상단: 테마 설명 대신 최초/최근 등장일, 총 리포트, 활성 주 수, 고유 애널리스트·데스크 수
- 주간 언급량 라인/막대 차트와 관련 산업 분포를 제공한다.
- 타임라인은 주차별로 `당시 핵심 주장 → 근거 리포트 → 리스크/반대 근거` 순으로 읽게 한다.
- 동일 애널리스트가 다수를 차지하면 `근거 집중` 경고를 표시한다.
- 서로 반대되는 관점을 자동 판정하는 기능은 만들지 않고, 구조화된 반대 근거가 생길 때까지
  편집된 주간 문장만 그대로 보여 준다.

### 5.5 산업 허브와 상세 — 산업 관점의 변화

**허브**

- 고정 분류 전체를 테이블로 보여 주되 `이번 주`, `최근 4주`, `전주 대비`, `최근 브리핑`,
  `연결 테마` 열을 제공한다.
- 리포트가 없는 산업도 0으로 남겨 분류 체계 전체와 데이터 공백을 확인하게 한다.

**상세**

- 최근 8주 언급량 스몰 차트, 관련 테마 순위, 최신 브리핑, 근거 리포트 순으로 배치한다.
- 브리핑이 없는 주는 리포트 건수와 함께 명시한다.
- 주간 브리핑의 표본 수와 고유 애널리스트 수를 항상 보인다.
- 목표주가 평균이나 투자의견 분포는 동일 종목의 시계열 정규화가 마련되기 전에는 제공하지 않는다.

### 5.6 탐색과 리포트 상세 — 모든 결론의 근거층

- 검색 범위는 제목·한 줄 요약·애널리스트에 한정되어 있음을 UI에 명시한다.
- 기간 필터, 활성 필터 칩, 전체 초기화, 결과 0건 안내를 추가한다.
- 결과 정렬은 `최신순`을 기본으로 하고 `관련도`는 검색 인덱스가 생기기 전에는 제공하지 않는다.
- 상세 페이지에 `이 리포트가 포함된 주간 인사이트/산업 브리핑` 역방향 링크를 제공한다.
- 수치 카드에는 단위와 원문 기준일을 표시하고, 숫자 파싱 실패 시 텍스트를 그대로 보존한다.

## 6. 시각화 명세

### A. 주간 테마 변화표 — 최우선

- **입력**: 선택 주와 직전 주의 개별 리포트 `themes`
- **집계 단위**: 테마별 고유 `report_id`
- **정렬**: 신규 우선 → 증감 내림차순 → 이번 주 건수 내림차순
- **표현**: 현재/직전 값을 모두 숫자로 보이고 색은 상태 보조 수단으로만 사용
- **빈 상태**: 직전 주 데이터가 없으면 비교 열 대신 `비교할 이전 주 데이터 없음`

### B. 테마×산업 히트맵 — 두 번째

- **입력**: 같은 리포트에 함께 태깅된 `themes[]`와 `industries[]`
- **셀 값**: 고유 리포트 수. 산업 또는 테마 미분류 건은 별도 `미분류` 축으로 숨기지 않는다.
- **정렬**: 행·열 합계 내림차순, 기본 최대 10×10; 나머지는 상세 표에서 확인
- **접근성**: 색상 외 숫자 레이블, 키보드 포커스, 동일 데이터를 표로 전환하는 토글 제공
- **주의**: 동시 태깅은 인과관계가 아니라 같은 리포트에서 함께 다뤄졌다는 뜻임을 툴팁에 표시

### C. 산업 관심도 스몰 멀티플 — 세 번째

- **입력**: 주차별 산업 태그의 고유 개별 리포트 수
- **범위**: 기본 최근 8주, 데이터가 부족하면 보유 기간 전체
- **표현**: 모든 산업에 동일한 y축을 사용해 크기 비교가 가능하게 한다.
- **보조 정보**: 브리핑 생성 기준선 2건, 해당 주 고유 애널리스트 수
- **금지**: 꺾은선 기울기를 상승/하락 전망으로 표현하지 않는다.

도넛 차트, 워드클라우드, 3D 차트, 장식용 게이지는 정밀 비교나 근거 추적에 불리하므로 사용하지 않는다.

라이브러리는 차트 종류가 많은지가 아니라 현재 Next.js 정적 빌드, React 컴포넌트, 한국어 라벨,
키보드 접근, 클라이언트 번들 크기와 맞는지를 기준으로 선택한다. 버전 번호를 문서에 고정하지 않고
구현 시점의 stable 버전을 lockfile에 고정한다.

### 권장 조합

#### 1. Apache ECharts — 관계와 추세만 담당

- `echarts/core`에서 `HeatmapChart`, `BarChart`, `LineChart`와 필요한 컴포넌트만 등록한다.
- 전체 `echarts`를 import하지 않고 tree-shaking 경로를 사용한다.
- 기본 렌더러는 SVG로 두어 작은 데이터셋의 선명도와 DOM 디버깅을 우선한다.
- Next.js에서는 차트 래퍼만 `"use client"`로 두고, 집계 데이터와 주변 설명은 서버 컴포넌트로 남긴다.
- 차트는 브라우저에서만 초기화하고 `ResizeObserver`로 컨테이너 크기 변경에 대응한다.
- `aria` 설명을 켜되 이것으로 접근성이 완성된다고 보지 않는다. 같은 데이터를 항상 HTML 표로 제공한다.
- 클릭 이벤트는 새 상태를 차트 내부에 감추지 않고 URL 검색 파라미터로 반영한다.

React wrapper인 `echarts-for-react`는 빠른 프로토타입에서는 쓸 수 있지만, 최종 구현에서는 얇은 내부 래퍼를
권장한다. 필요한 생명주기(`init`, `setOption`, `resize`, `dispose`)가 작고, wrapper 호환성에 의존하지 않으며,
등록한 차트만 번들에 넣기 쉽기 때문이다.

#### 2. TanStack Table — 숫자의 근거를 비교하는 표

- 주간 테마 변화표와 테마·산업 허브의 정렬·필터 모델에만 사용한다.
- 서버가 만든 행 데이터를 넘기고, 컬럼과 정렬 상태만 클라이언트에서 관리한다.
- 기간·정렬·필터 상태는 `?period=4w&sort=delta&industry=반도체`처럼 URL에 직렬화한다.
- 가상 스크롤은 처음부터 넣지 않는다. 실제 행이 수백 개를 넘고 측정 결과가 필요할 때만 검토한다.
- 모바일에서는 열을 숨기는 대신 `이름/변화/근거 수`를 1차 행에 남기고 나머지를 펼침 영역으로 보낸다.

#### 3. Lucide React — 스캔 속도 보조

- 신규, 확대, 약화, 경고, 원문 이동에 같은 아이콘을 일관되게 쓴다.
- 아이콘 옆에는 반드시 `신규`, `근거 집중` 같은 텍스트 라벨을 둔다.
- 개별 아이콘만 import하고 장식 목적으로 늘리지 않는다.

### 라이브러리보다 먼저 적용할 표현 규칙

라이브러리를 추가해도 카드마다 긴 문단을 그대로 두면 달라지지 않는다. 다음 규칙을 먼저 적용한다.

- **한 화면 한 질문**: 홈은 “무엇이 달라졌나”, 주간은 “왜 달라졌나”, 상세는 “근거가 무엇인가”에 답한다.
- **요약 기본값**: 홈 설명은 최대 2줄, 테마당 핵심 문장 1개만 노출하고 나머지는 펼친다.
- **숫자+명사**: `5` 대신 `이번 주 5건`, `+2` 대신 `전주 대비 +2건`으로 쓴다.
- **색의 역할 제한**: 신규=파랑, 확대=초록, 약화=회색, 경고=주황으로 고정하며 빨강/초록만으로 구분하지 않는다.
- **카드 수 제한**: 첫 화면은 상태 바 1개, 핵심 서사 1개, 변화 목록 1개, 관계 차트 1개만 우선 노출한다.
- **세부 정보 지연 공개**: 애널리스트·데스크 다양성과 전체 근거 목록은 hover가 아닌 클릭/펼침으로 제공한다.
- **차트 제목을 결론형으로**: `테마 동향` 대신 `이번 주 새 테마 3개, 금리 이슈는 2주 연속 확대`처럼 쓴다.

### 1일 기술 검증(Spike) 통과 조건

실제 의존성을 확정하기 전에 별도 브랜치에서 동일한 작은 데이터셋으로 ECharts와 현재 CSS 기반 표를 만든다.

1. W39/W40 데이터를 이용한 5×8 heatmap이 SSR 오류 없이 정적 빌드된다.
2. 셀 클릭 시 산업·테마가 URL에 남고 뒤로 가기가 동작한다.
3. 360px에서 차트 대신 표로 전환해 값이 잘리지 않는다.
4. 키보드만으로 같은 근거 목록에 도달한다.
5. 프로덕션 JS 증가량을 측정하고, 차트 코드가 홈 외 페이지에 불필요하게 포함되지 않는다.
6. 시각화와 표의 모든 셀 값을 자동 테스트로 비교한다.

하나라도 실패하면 heatmap은 CSS Grid 기반 정적 표로 먼저 출시한다. 시각적 화려함보다 비교 가능성과
근거 연결이 우선이므로 ECharts 도입 자체를 완료 조건으로 삼지 않는다.

## 8. 필요한 데이터 모델과 계산 규칙

빌드 때 매번 원문 전체를 클라이언트로 보내지 말고, 서버 빌드 단계에서 다음 경량 집계를 생성한다.

```ts
type DashboardSnapshot = {
  generatedAt: string;
  latestPublishedDate: string | null;
  quality: { total: number; unsummarized: number; pdfErrors: number };
  weeks: Array<{
    week: string;
    startDate: string;
    endDate: string;
    reportCount: number; // individual만
    themes: Array<{
      name: string;
      reportIds: string[];
      analystCount: number;
      deskCount: number;
      industries: Record<string, number>;
    }>;
    industries: Array<{
      name: string;
      reportIds: string[];
      analystCount: number;
      briefExists: boolean;
    }>;
  }>;
};
```

계산 규칙은 한 곳에서 함수로 관리하고 단위 테스트한다.

1. 집계 대상은 `report_type === "individual"`인 리포트만 사용한다.
2. 하나의 리포트 안에서 중복 태그가 있어도 한 번만 센다.
3. 주차는 현재 파이프라인과 동일한 UTC 기준 ISO 주차를 사용한다.
4. 전주 비교는 달력상 직전 ISO 주차로 하며, 데이터가 없는 주를 이전 관측 주로 대체하지 않는다.
5. `신규/확대/지속/약화`는 절대 건수로 계산한다. 비율은 표본이 작을 때 과장되므로 보조로도 쓰지 않는다.
6. 애널리스트가 비어 있으면 다양성 분모에서 제외하고 `미상 n건`을 별도로 표시한다.
7. 테마 별칭 병합 후의 대표 이름만 집계하고, 별칭 변경 시 모든 과거 스냅샷을 재생성한다.
8. 모든 세부 숫자는 클릭해 그 숫자를 구성한 리포트 ID 목록을 확인할 수 있어야 한다.

장기적으로 주가·실적·컨센서스를 결합하려면 `ticker`, 기준 통화, 기준일, 조정주가, 데이터 출처와
라이선스를 별도 모델로 먼저 정의한다. PDF 텍스트에서 임의 추출한 숫자를 차트 데이터로 바로 쓰지 않는다.

## 9. 구현 단계

### Phase 0 — 계측 기준과 데이터 품질 (0.5~1일)

- [ ] 집계 정의와 제외 규칙을 코드 상수/문서로 고정
- [ ] 현재 데이터의 미요약, PDF 오류, 미분류 산업·테마, 빈 애널리스트 비율 검사
- [ ] 3개 표본 주차를 손계산해 자동 집계 결과와 대조할 fixture 작성
- [ ] `DashboardSnapshot` 생성 함수와 단위 테스트 추가

**완료 조건**: 같은 필터에서 카드 숫자, 차트 숫자, 근거 목록 건수가 일치한다.

### Phase 1 — 차트 없이 정보 구조 검증 (1~2일)

- [ ] 홈을 상태 바 → 주간 한눈에 → 변화표 → 최신 핵심 → 최근 리포트 순으로 재배치
- [ ] 주간 페이지에 전주 비교 테이블과 근거 리포트 링크 추가
- [ ] 테마·산업 허브를 누적 칩/목록에서 비교 테이블로 변경
- [ ] 공통 기간 필터와 URL 상태 적용
- [ ] 모바일 360px, 태블릿 768px, 데스크톱 1280px에서 정보 우선순위 확인
- [ ] 긴 설명은 2줄 요약+펼침으로 바꾸고 결론형 제목을 적용

**완료 조건**: 차트 없이도 최신 변화와 그 근거에 3번 이하 클릭으로 도달한다.

### Phase 2 — 핵심 시각화 (2~3일)

- [ ] `echarts/core` 기반 테마×산업 히트맵과 동일 데이터 표 구현
- [ ] ECharts 기반 산업 관심도 스몰 멀티플 구현
- [ ] 테마 상세 스파크라인과 근거 집중 경고 구현
- [ ] TanStack Table 기반 변화표의 URL 정렬·필터 구현
- [ ] 프로덕션 JS 크기와 hydration 범위를 도입 전후로 측정

변화표는 HTML/CSS를 유지하고 관계·추세 차트에만 ECharts를 사용한다. 축·툴팁이 필요 없는 작은 상태 표시는
CSS로 구현하며, 클라이언트 번들 증가는 프로덕션 빌드 결과로 확인한다.

**완료 조건**: 마우스 없이 셀을 탐색하고, 모든 그래픽 값을 표 또는 텍스트로도 확인할 수 있다.

### Phase 3 — 드릴다운과 사용성 보강 (1~2일)

- [ ] 차트 클릭 시 교차 필터된 리포트 목록 또는 상세 URL로 이동
- [ ] 리포트 상세에 주간·산업 브리핑 역링크 추가
- [ ] 활성 필터 칩, 초기화, 빈 상태, 데이터 부족 메시지 정리
- [ ] 시각화 설명과 `투자 신호가 아님` 안내 추가
- [ ] 실제 사용자 과업 5개를 관찰하고 순서·문구 조정

**완료 조건**: 아래 성공 지표를 계측하거나 수동 사용성 테스트로 확인할 수 있다.

### Phase 4 — 데이터가 충분해진 뒤 검토

- 8주 이상: 8주 기준선 대비 이례적 언급 증가 표시
- 12주 이상: 테마 지속 기간과 재등장 간격 제공
- 외부 정형 데이터 확보 후: 가격·실적 변화와 리서치 관점의 병렬 비교
- 사용 패턴이 확인된 뒤: 관심 테마 저장과 신규 등장 알림

## 10. 검증 계획과 성공 지표

### 기능·데이터 검증

- 집계 단위 테스트: ISO 연도 경계, 빈 주, 중복 태그, 별칭, 미분류, `daily_series` 제외
- 링크 테스트: 모든 차트/표의 리포트 ID가 실제 상세 페이지에 존재
- 빌드 테스트: 저장소 전체 데이터로 정적 생성 성공
- 회귀 테스트: 기존 로그인, 주간·일간·리포트 상세 접근 유지
- 접근성: 키보드 이동, 포커스 표시, 명암, 색상 외 상태 표현, 표 대체 뷰
- 반응형: 360/768/1280px에서 표가 내용을 숨기지 않고 가로 스크롤 또는 카드형으로 전환

### 사용자 과업 성공 기준

1. 최신 발행일과 파이프라인 상태를 **10초 이내** 확인한다.
2. 이번 주 새로 등장하거나 확대된 테마 하나를 **30초 이내** 찾는다.
3. 해당 테마와 가장 많이 연결된 산업 및 근거 리포트에 **3클릭 이내** 도달한다.
4. 산업의 최근 변화가 `리포트 관심도`임을 오해 없이 설명한다.
5. 요약에서 증권사 원문까지 **2클릭 이내** 도달한다.

분석 도구를 추가한다면 원문 제목이나 검색어처럼 민감할 수 있는 값은 보내지 않고, `페이지 종류`,
`필터 사용`, `근거 열기`, `원문 이동` 같은 익명 이벤트만 수집한다. 개인용 배포에서는 분석 도구 없이
5개 과업을 직접 수행하며 걸린 시간과 실패 지점을 기록하는 것으로 충분하다.

### 성능 예산

- 홈 초기 로드에 `pdf_text`를 포함하지 않는다.
- 차트 데이터는 최근 8주 기본 범위로 제한하고 상세 목록은 필요할 때만 렌더링한다.
- Core Web Vitals 측정 시 정적 콘텐츠의 이점을 유지하고, 필터·차트만 클라이언트 컴포넌트로 둔다.
- 접근 권한이 있는 환경에서 Lighthouse 성능·접근성 각각 90 이상을 목표로 한다.

## 11. 위험과 대응

| 위험 | 잘못된 해석/영향 | 대응 |
|---|---|---|
| 적은 표본 | 1→2건을 큰 추세로 오해 | 절대 건수, `n`, 데이터 부족 문구 우선 |
| 동일 애널리스트 반복 | 여러 독립 근거로 오해 | 고유 애널리스트 수와 집중 경고 |
| 태그 품질·별칭 변경 | 가짜 신규 테마 발생 | 대표 이름으로 재집계, 별칭 회귀 테스트 |
| 일간 종합물 중복 | 테마 빈도 부풀림 | 기본 집계에서 `daily_series` 제외 |
| 차트 과잉 | 읽어야 할 서사보다 장식이 앞섬 | 핵심 3종만 도입, 모든 차트에 과업 정의 |
| 외부 시장 데이터 부재 | 언급량을 성과로 오인 | `리포트 언급량` 라벨, 가격 차트 제외 |
| 정적 빌드 데이터 증가 | 빌드/번들 지연 | 빌드 집계, 원문 제외, 기간 제한 |
| 원문·개인정보 노출 | 비공개 자료 재배포 | 기존 인증 유지, 분석 이벤트 최소화 |

## 12. 이번 구현에서 하지 않을 것

- 매수/매도 점수, 종목 랭킹, AI 감성 게이지
- 외부 출처 없이 계산한 목표주가 상승여력과 기대수익률
- 리포트 언급량과 주가의 인과관계 주장
- 원문 텍스트를 브라우저로 보내는 전체 본문 검색
- 표본이 충분하지 않은 장기 추세·계절성 분석
- 네트워크 그래프, 워드클라우드 등 탐색 경로가 불명확한 시각화
- 사용자 계정, 포트폴리오, 실시간 알림

이 범위 통제가 중요한 이유는 현재 제품의 강점이 이미 생성된 **편집된 요약과 근거 연결**에 있기 때문이다.
첫 번째 시각화 버전은 그 연결을 더 빠르게 읽게 해야지, 데이터가 답할 수 없는 투자 판단을 대신해서는 안 된다.
